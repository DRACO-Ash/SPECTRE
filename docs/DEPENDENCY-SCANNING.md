# Dependency Scanning: diagnosis and evidence

**Root cause found and fixed in 0.4.5.** No vulnerable package was ever
involved. `requirements.txt` was not recognisable as a pip-compile lockfile, so
the analyser's parser skipped it, produced no Software Bill of Materials (SBOM)
and exited non-zero.

## What the platform reported

```
[INFO] [dependency-scan-python] repository dependency-scan-python analyzer v6.6.1
[INFO] [dependency-scan-python] Detected supported dependency files in '.'.
exit status 1
WARNING: **/gl-sbom-*.cdx.json: no matching files.
WARNING: gl-dependency-scanning-report.json: no matching files.
```

Three seconds from start to exit, no error text, no report. A scan that finds
vulnerabilities writes a report naming them. The platform's interface maps a
non-zero exit to "Vulnerable dependencies found", so a **crashed scan is
presented as a finding**. That mapping sent this submission hunting for a CVE
three times.

## Root cause

Read from the analyser's own source
(`gitlab-org/security-products/analyzers/dependency-scanning`):

1. The analyser selects a package manager from the files present. With both
   `requirements.txt` and `pyproject.toml` at the root it selects **pip-tools**
   (`pm/package_manager.go`, `PackageManagerPipTools`), which registers
   `requirements.txt` as the lockfile and `pyproject.toml` as its source.
2. For that pairing, `config/parser.go` routes `requirements.txt` to the
   **pip-compile parser**.
3. That parser calls `common.IsPipCompileLock`, which accepts a file only if
   line 1 begins with the uv header **or line 2 begins with**
   `# This file is autogenerated by pip-compile with`.
4. Our `requirements.txt` opened with a hand-written banner:

   ```
   # SPECTRE dependency manifest for the Bluestaq App Store pipeline.
   #
   aiosqlite==0.22.1
   ```

   Line 2 is `#`. The check is **positional**, so the parser returned
   `SkipParser`, nothing produced an SBOM, and the job exited 1.

`requirements.lock` carried the correct header all along but is not a filename
the analyser detects, so it was never read.

## The fix

`requirements.txt` is now generated by `pip-compile` rather than maintained by
hand, so it carries the standard header and `# via` provenance annotations:

```
pip-compile --extra test --strip-extras --output-file=requirements.txt pyproject.toml
```

The package set is byte-for-byte the same 54 packages at the same versions.
Nothing was added, removed or upgraded. The file is now a genuine lockfile with
transitive attribution, which is better than what it replaced.

`TestPipCompileLockContract` guards it, replicating `IsPipCompileLock` exactly.
Adding a single banner line above the generated header makes it fail, which is
how the regression was verified.

## Evidence the tree is clean

Checked against the scanner's own database, not just our own tooling:

● **GitLab `gemnasium-db`**, cloned and matched offline against every pinned
  version with OR-aware range parsing.
  ● 54 packages in `requirements.txt`: 94 advisories examined, **0 affected**.
  ● 43 development-only packages: 54 advisories examined, **0 affected**.
● **pip-audit** against `requirements.txt`, `requirements.lock` and full
  `pyproject.toml` resolution: no known vulnerabilities in all three.
● **Vendored JavaScript**, fingerprinted by hand since it ships without a
  manifest: htmx 1.9.12, Chart.js 4.4.7, chartjs-plugin-zoom 2.0.1,
  Hammer.js 2.0.7. The only advisory on file for any of them is CVE-2020-7746
  against Chart.js `<2.9.4`; we ship 4.4.7.

## A correction

An earlier revision of this document blamed the analyser's Python version,
reasoning that `pip download` could not resolve our 3.12-only pins on an older
interpreter. That was wrong. The Test stage log shows the analyser environment
running Python 3.12.14 and resolving every wheel, and the scan job exits after
three seconds, far too fast to have attempted a download. The parser check
above is the actual cause.

`scripts/audit-dependencies.sh` still reports the interpreter floor, which
remains worth knowing, but it is not why this stage failed.

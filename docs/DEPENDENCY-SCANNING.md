# Dependency Scanning: diagnosis and evidence

**Root cause found in 0.4.5 and verified in 0.4.6 by running the analyser
itself.** No vulnerable package was ever involved. `requirements.txt` was not
recognisable as a pip-compile lockfile, so the parser skipped it, no Software
Bill of Materials (SBOM) was produced, and the analyser aborted.

## What the platform reported

```
[INFO] [dependency-scan-python] repository dependency-scan-python analyzer v6.6.1
[INFO] [dependency-scan-python] Detected supported dependency files in '.'.
exit status 1
WARNING: **/gl-sbom-*.cdx.json: no matching files.
WARNING: gl-dependency-scanning-report.json: no matching files.
```

No error text and no report. The platform maps a non-zero exit to "Vulnerable
dependencies found", so a crashed scan is presented as a finding. That mapping
cost this submission four cycles.

## What the analyser actually says

The analyser is open source, so it can be built and run against a package
locally. `scripts/verify-dependency-scan.sh` does exactly that, and it prints
the message the platform swallows:

```
[WARN] parsing error parsing file requirements.txt:
       expected pip-compile lock file but found plain manifest
[FATA] manifest fallback is disabled and no usable lock or dependency graph
       file was found for: [requirements.txt].
```

## Root cause

1. With both `requirements.txt` and `pyproject.toml` at the root, the analyser
   selects the **pip-tools** package manager (`pm/package_manager.go`), which
   registers `requirements.txt` as the lockfile.
2. `config/parser.go` routes that pairing to the **pip-compile parser**.
3. That parser calls `common.IsPipCompileLock`, which accepts a file only if
   line 1 begins with the uv header **or line 2 begins with**
   `# This file is autogenerated by pip-compile with`.
4. Our `requirements.txt` opened with a hand-written banner, so line 2 was `#`.
   The check is **positional**. The parser returned `SkipParser`, manifest
   fallback is disabled by default, and the run aborted.

`requirements.lock` carried the correct header all along, but `.lock` is not a
filename the analyser detects, so it was never read.

## The fix

`requirements.txt` is now generated by `pip-compile` rather than maintained by
hand:

```
pip-compile --extra test --strip-extras --output-file=requirements.txt pyproject.toml
```

The package set is the same 54 packages at the same versions. Nothing was
added, removed or upgraded. The file now carries `# via` provenance
annotations, which is better than what it replaced.

Measured against the real analyser:

| Package | Exit | SBOM |
|---|---|---|
| 0.4.4 shape (hand-written banner) | 1 | none |
| 0.4.5 onward (pip-compile output) | **0** | **`gl-sbom-pypi-pip.cdx.json`, 54 components, 22 graph entries** |
| docker-only | **0** | none, correctly: it ships no manifest |

## Preventing a recurrence

● `scripts/verify-dependency-scan.sh` builds the analyser and runs it against a
  built package. The packager calls it on every build and refuses to ship a
  package the analyser rejects. Set `SKIP_DS_VERIFY=1` to bypass, or
  `DS_ANALYZER_BIN` to reuse a prebuilt binary.
● `TestPipCompileLockContract` replicates `IsPipCompileLock` offline, so the
  check still holds without Go or network.
● The packager also runs the whole test suite from inside the built zip, after
  a contract test passed locally and failed in the package.

## Evidence the tree is clean

Checked against the scanner's own database, not just our own tooling:

● **GitLab `gemnasium-db`**, cloned and matched offline against every pinned
  version with OR-aware range parsing.
  ● 54 packages in `requirements.txt`: 94 advisories examined, **0 affected**.
  ● 43 development-only packages: 54 advisories examined, **0 affected**.
● **pip-audit** against `requirements.txt`, `requirements.lock` and full
  `pyproject.toml` resolution: no known vulnerabilities in all three.
● **Vendored JavaScript**, fingerprinted by hand since it ships without a
  manifest: htmx 1.9.12, Chart.js 4.4.7, chartjs-plugin-zoom 2.0.1,
  Hammer.js 2.0.7. The only advisory on file for any of them is CVE-2020-7746
  against Chart.js `<2.9.4`; we ship 4.4.7.

## A correction

An earlier revision of this document blamed the analyser's Python version,
reasoning that `pip download` could not resolve our 3.12-only pins on an older
interpreter. That was wrong. The Test stage log shows the analyser environment
running Python 3.12.14 and resolving every wheel, and the scan job exits after
three seconds, far too fast to have attempted a download. The parser check
above is the actual cause.

`scripts/audit-dependencies.sh` still reports the interpreter floor, which
remains worth knowing, but it is not why this stage failed.
